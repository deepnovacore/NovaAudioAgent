# Codex 项目操作确认的用户体验问题与预期方案

状态：讨论稿
日期：2026-08-26

## 1. 摘要

Nova Audio Agent 对创建 Workspace、切换 Workspace 和恢复 Session 采用两阶段确认：Nova
先生成操作提案，用户明确确认后，宿主才真正提交操作。这一授权边界本身是必要的，但当前产品没有
可靠地把“正在等待用户确认”传达给用户。

一次实际使用中，用户要求 Nova 创建俄罗斯方块小游戏。Nova 正确生成了创建 `tetris-game`
Workspace 的提案，宿主也生成了“请确认或取消”的提示，但语音只播报“我来为你创建一个开发任务”，
桌面则显示“Codex 等待确认”。用户因此合理地认为任务已经交给 Codex，或者 Codex 正在等待后台权限；
实际上 Codex 尚未启动，系统正在等待用户再次说“确认”。

建议将项目边界确认视为宿主负责的结构化交互，而不是普通的异步任务结果。所有语音模式都应让模型收到
完整确认内容并受约束地自然提问；桌面则提供不依赖模型的确定性兜底，明确显示“等待你的确认”、目标
Workspace 或 Session、尚未提交以及有效时间。确认前不得使用暗示任务已经提交的措辞。

## 2. 背景

Nova 的项目模型包含两个核心概念：

- Workspace 是文件系统和 Git 项目的隔离边界；
- Session 是 Workspace 内可恢复的 Codex thread。

创建或改变 Workspace、恢复历史 Session 都会改变 Codex 后续工作的目标边界，因此采用提案与确认分离的
授权机制：

1. 模型通过 `codex__project` 提出操作；
2. 宿主验证目标并生成一次性 proposal；
3. 用户下一轮明确确认或取消；
4. 模型调用 `codex__confirm_project_action`，携带匹配的 proposal ID 和 JSON boolean；
5. 宿主验证并消费一次性授权；
6. 只有确认成功后才创建或切换 Workspace、恢复 Session，必要时启动 Codex。

该流程可以防止模型在缺少用户授权时改变项目边界，也能抵御确认重放、错误 proposal ID 和过期确认。
问题不在授权模型本身，而在授权状态没有被正确呈现给用户。

## 3. 复现场景

用户说：

> 帮我写一个俄罗斯方块小游戏。

模型将其识别为独立项目，并请求：

```json
{
  "action": "create_workspace",
  "workspace": "tetris-game",
  "work_order": "..."
}
```

宿主返回一个 `confirmation_required` 结果，其中包含：

```json
{
  "code": "confirmation_required",
  "action": "create_workspace",
  "workspace": "tetris-game",
  "confirmation_prompt": "准备创建工作区tetris-game，并在其中开始任务，请确认或取消。"
}
```

但用户实际听到的是：

> 好的，我来为你创建一个俄罗斯方块小游戏的开发任务。

桌面状态显示：

> Codex 等待确认

此时的真实状态是：

- Workspace 尚未创建；
- Session 尚未创建；
- Codex app-server 尚未启动；
- 系统正在等待用户确认；
- proposal 会在 90 秒后过期。

## 4. 问题分析

### 4.1 确认问题没有确定性地到达用户

宿主已经生成包含完整操作信息的 `confirmation_prompt`，但它没有进入实时模型的上下文。当前
`codex__project` 被统一声明为异步结果，bridge 会先返回 `accepted` 并建立
`delegation_acknowledgement`；模型因此只拿到工作单摘要和普通接单语义。

真正携带 `confirmation_prompt` 的异步 Handoff 随后经过 `finalSpeechView`。由于确认提案没有
`final_message` 字段，这一安全投影会丢弃动作、目标和确认提示，退化成“Codex 任务未能确认完成
（confirmation_required）”。模型最终只能看到这条错误的派生事实，而不是确认问题本身。

因此问题不只是模型偶尔漏说，而是当前数据流没有向模型提供可正确转述的确认内容。系统内部虽然安全地
停在待确认状态，但用户不知道需要采取什么动作，因此安全流程在体验上表现为“任务卡住”。

### 4.2 确认前的措辞暗示操作已经执行

“我来为你创建任务”通常会被用户理解为操作已经接受或正在执行。实际上系统只创建了 proposal。
这使用户对任务生命周期形成错误判断，也会导致后续询问集中在后台权限、Codex 状态或任务进度上。

### 4.3 桌面状态指向了错误主体

“Codex 等待确认”把等待动作归因给 Codex，但 Codex 此时尚未启动。真正等待的是 Nova 的宿主授权流程，
需要采取动作的是用户。

状态文案应回答“谁需要做什么”，而不是只暴露内部模块名称。

### 4.4 超时闭环存在，但播报仍非确定性

proposal 的有效期是 90 秒。现有实现会在到期后使 proposal 失效、清除 pending、收尾挂起工具调用、
必要时重连 provider，并排入“确认已过期，本次操作已取消”的语音事实。需要保留这一闭环。

缺口在于过期提示仍要由模型转述，措辞没有确定性保证；服务关闭期间，provider-facing 的播报步骤也会被
跳过。桌面必须确定性地清除等待状态，语音侧则需要回归测试保证正常运行时能够收到明确的过期事实。

## 5. 设计目标

预期方案应满足以下目标：

1. 用户在一次正常交互中必然知道系统准备执行什么操作；
2. 用户明确知道操作尚未执行，以及需要确认或取消；
3. UI 能区分用户授权状态与 Codex 执行状态；
4. 保留现有一次性 proposal、严格 ID 绑定、超时和防重放机制；
5. 即使实时模型漏说、说错或没有继续生成回复，授权提示仍然在桌面可见；
6. 确认、取消和超时都形成完整、可观察的状态闭环。

## 6. 预期方案

### 6.1 修复确认结果的数据流并使用受约束转述

`create_workspace`、`select_workspace` 或 `resume_session` 返回 `confirmation_required` 后，宿主应把
结构化 proposal 转换为专用确认事实，使完整动作、目标、“尚未执行”和确认要求进入实时模型上下文；
同时为该响应提供明确约束，要求模型说明操作并询问用户是否确认或取消。

建议确认内容至少包含：

- 即将执行的动作；
- 目标 Workspace；
- 目标 Session（如适用）；
- 是否会立即开始任务；
- “确认”或“取消”的明确行动提示。

例如：

> 我准备新建工作区“tetris-game”，并在其中开始俄罗斯方块开发任务。是否确认？

语音底线是受约束转述，不要求跨 provider 逐字朗读模板。集成 realtime 模式的音频由模型直接生成，没有
可绕过模型的独立 TTS；级联模式虽有独立 TTS 接缝，但不应据此建立两套授权语义。以下内容必须进入模型
上下文并由响应约束覆盖：操作目标、尚未执行、需要用户确认。

实现还应消除两条误导路径：项目边界提案不能先产生暗示已提交的普通接单语；`finalSpeechView` 不能再把
`confirmation_required` 退化为完成状态不明的错误文案。

### 6.2 将确认作为独立状态，而不是 Codex 工作状态

桌面应将 Workspace 授权和 Codex 执行拆成两个正交状态：

- 授权状态：无待确认 / 等待用户确认 / 正在提交 / 已取消 / 已超时；
- Codex 状态：未启动 / 正在启动 / 工作中 / 空闲 / 失败。

紧凑状态建议将“Codex 等待确认”改为：

> 等待你的确认

展开状态可以显示：

> 准备创建工作区“tetris-game”
> 等待你的确认，90 秒后自动取消
> Codex 尚未启动

当前 `codex.project` 协议只有当前 Workspace、当前 Session 和 pending boolean，无法表达上述信息。
需要同步扩展 runtime wire、desktop bridge 和 renderer 的精确键集校验，增加待确认动作、目标和相对有效
时间。相对剩余秒数用于 UI，不直接把 runtime Clock 的绝对时刻当作墙钟时间。

### 6.3 收紧确认前后的生命周期措辞

确认前只允许使用提案语义，例如：

- “我准备……”；
- “计划创建……”；
- “是否确认？”；
- “确认后我会提交给 Codex。”

确认前不应使用：

- “我来创建”；
- “任务已经安排”；
- “已经提交”；
- “Codex 已经开始处理”。

确认成功且宿主接受提交后，才可以播报：

> 已确认，任务已提交，Codex 正在启动。

Codex 真正报告启动后，再进入“Codex 正在工作”状态。确认成功与 Codex 启动成功仍应是两个不同的事实。

### 6.4 保持现有确认安全边界

现有实现已经把待确认期间的下一条语音保留给确认控制器，并按语义映射：

- “确认”“可以”“开始吧”映射为 `confirmed=true`；
- “取消”“不要创建”“先等等”映射为 `confirmed=false`；
- 无法明确判断的回答不提交操作，并再次简短询问。

proposal ID 绑定、保留的用户 item、严格 JSON boolean、对象同一性的一次性消费和防重放均已实现。本次
改动不得重写或放宽这些边界，而应通过现有测试和新增回归测试证明它们未被破坏。

桌面后续可以增加“确认”和“取消”按钮，但按钮必须复用同一个 proposal ID 和一次性消费机制，不能建立
第二条权限较弱的提交路径。

### 6.5 确认超时必须结束等待状态

proposal 超过 90 秒后，宿主应：

1. 使 proposal 失效；
2. 清除桌面的等待确认状态；
3. 保证操作没有执行；
4. 明确告知用户结果。

建议提示：

> 创建工作区的确认已超时，本次操作没有执行。需要的话可以重新发起。

## 7. 建议状态流

```text
用户提出开发请求
        │
        ▼
模型请求项目边界操作
        │
        ▼
宿主验证并创建 proposal
        │
        ▼
宿主明确提问 + UI 显示“等待你的确认”
        │
        ├── 用户确认 ──► 宿主验证并消费 proposal
        │                         │
        │                         ├── 提交成功 ──► 启动 Codex ──► Codex 工作中
        │                         └── 提交失败 ──► 明确报告未执行
        │
        ├── 用户取消 ──► 清除 proposal ──► 明确报告已取消
        │
        └── 90 秒超时 ─► 清除 proposal ──► 明确报告未执行
```

## 8. 方案取舍

### 推荐：修复数据流 + 受约束转述 + UI 确定性兜底

提案生成时把结构化确认事实交给模型并要求其自然提问，同时修改 UI 协议、状态和生命周期措辞。这一方案
同时解决授权提示丢失、状态主体错误和超时可见性问题，也符合“宿主拥有授权和任务生命周期”的现有
架构原则。

### 不建议仅修改模型提示词

当前确认内容根本没有进入模型上下文，因此只增加“必须询问用户是否确认”的提示不会生效。即使数据流
修复后，模型输出仍不是确定性协议，提示词也不能替代桌面兜底。

### 不建议仅修改桌面文案

把“Codex 等待确认”改成“等待你的确认”可以降低歧义，但纯语音场景仍然缺少明确问题，也不能修复模型
暗示任务已经提交的问题。

## 9. 验收标准

1. 产生 `confirmation_required` 后，用户一定能听到或看到明确的确认问题；
2. 确认问题明确描述动作、目标和“尚未执行”的状态；
3. 用户确认前不会创建或切换 Workspace、恢复 Session 或启动相应 Codex 任务；
4. 桌面显示“等待你的确认”，不再显示“Codex 等待确认”；
5. 等待确认期间，Codex 状态显示“尚未启动”或真实的独立状态；
6. 回归测试继续证明：用户明确确认后，正确 proposal 只能被消费一次；
7. 回归测试继续证明：取消、错误 proposal ID、重放和过期 proposal 均不能触发操作；
8. 确认成功但提交失败时，Nova 必须明确说明操作未执行；
9. proposal 超时后，等待状态自动清除并向用户说明本次操作没有执行；
10. 宿主级集成测试证明：提案的动作、目标、“尚未执行”和确认要求进入 provider 上下文；
11. `start_session` 等不需要改变 Workspace 边界的现有路径不被意外增加额外确认；
12. 语音确认与未来可能增加的 UI 按钮共享同一授权控制器，不产生旁路。

## 10. 非目标

本方案不讨论以下事项：

- 放宽或移除 Workspace 边界确认；
- 改变 Workspace 与 Session 的产品定义；
- 修改 Codex 自身的 sandbox 或审批机制；
- 将 proposal ID 暴露给用户；
- 为所有普通 Codex Session 启动增加确认；
- 通过自动确认来绕过用户授权。

## 11. 待讨论问题

1. UI 第一版显示静态剩余秒数还是本地倒计时？两者都必须使用相对时长，不得把 runtime Clock 的绝对值
   当作墙钟时刻。
2. 第一版是否同时加入确认/取消按钮？桌面目前没有向 runtime 提交决策的通道，按钮属于新增授权入口，
   建议本轮不做，但协议设计应预留复用同一确认控制器的可能。
3. 对“独立项目”和“当前 Workspace 内新 Session”的路由，是否需要在自然语言中更主动地说明差异？

## 12. 相关实现位置

- `runtime/src/realtime/project-confirmation.ts`：proposal、确认提示、90 秒超时和一次性授权；
- `runtime/src/realtime/service.ts`：确认语音保留、结构化决策、提交和超时清理；
- `runtime/src/realtime/qwen.ts`：实时模型对 Workspace、Session 和确认工具的行为说明；
- `runtime/src/executors/codex-project-live.ts`：项目操作提案与确认后提交；
- `desktop/ambient-orb/src/renderer/state.mjs`：桌面状态中的“Codex 等待确认”文案。

## 13. 设计原则

项目边界确认属于授权协议，而不是普通对话内容。安全性不仅要求“没有确认就不执行”，也要求用户能够
理解系统正在等待什么、为什么没有执行，以及接下来应该做什么。因此，确认意图必须由宿主和 UI
确定性保证，不能仅依赖模型遵循提示词。
